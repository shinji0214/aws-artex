## 方針

「構築に成功しました」という手順記事ではなく、**ARTEXの規約でEC2を断念 → ローカルにAWS風ログ環境を再構築 → haikuで検証 → sonnetは載せられなかった** という、方針転換と試行錯誤の体験談にする。
1本にまとめる想定。長くなりすぎたら、§7〜§8 を「ログ編」として2本目に分ける。

**仮タイトル案**
- 「AIペンテストツールARTEXをAWSで試すはずが、規約を読んでローカルに作り直した話」
- 「ARTEXの攻撃はログにどう見えるのか — ALB形式のログをローカルで再現して観察する」
- 「AIペンテスター(haiku)は6分半でJuice Shopを18問解いた。そのときログには何が残ったか」

**想定読者:** AWSは触ったことがあり、AIペンテスターの動きと、攻撃が防御側のログにどう出るかを知りたい人

## 構成

1. **はじめに**
   - 動機: 攻撃者視点（AIペンテスター）と防御側のログを両方見たい
   - 結論を先に: 「AWSではやらず、ローカルにAWS風ログ環境を作った。haikuで6分半・634リクエスト・18問攻略。その足跡がログにどう残ったか」

2. **最初の計画: AWSに検証環境を作る**（短く）
   - 当初の構成図（A-1）。Terraform で EC2 + Juice Shop + Flow Logs / CloudTrail / CloudWatch
   - admin を使わない IAM（A-2）、構築完了（A-3）
   - コラム: Fargate の vCPU 上限、PassRole 不足などのハマりどころ（A-4）

3. **規約の壁: 自分の環境でもネットワーク越しはダメだった**（記事の転換点）
   - ARTEX同梱の利用規約の該当箇所（B-1。引用は最小限＋出典）
   - 「自己所有だからOK」ではなく、ツール側の規約にも従う必要がある（B-2）
   - AWS環境は destroy（A-5）
   - 読者への注意: ペンテストツールを使う前に、対象の権限とツールの規約の両方を確認する

4. **ローカルに「AWS風ログ環境」を作り直す**
   - 構成図（C-1）: ARTEX → nginx(127.0.0.1:8080) → Juice Shop(内部3000)。すべてローカルで完結
   - AWSとの対応表（B-3）
     | AWS | ローカルでの代替 |
     |---|---|
     | ALB Access Logs | nginx（ALB形式）→ `alb_access.log` |
     | CloudWatch Logs（アプリ） | Juice Shop の stdout |
     | VPC Flow Logs | 今回は見送り |
     | CloudTrail | 等価物なし（§8で説明） |
   - nginx の `log_format` で ALB 形式を再現する（C-2, C-3）
   - 平常時のログ（C-7）

5. **ARTEX を走らせる（Run1: haiku）**
   - セットアップ: APIキーが必要（サブスクでは動かない）、既定モデルは高いので haiku に変更（D-1, D-2）
   - タスク作成: 対象は `http://host.docker.internal:8080/`（D-3）
   - Planner の計画、Worker の動き、SQLi を試す様子（D-4〜D-7）
   - 結果: 約6分35秒・634リクエスト・Findings 3/7/8/3（D-8〜D-10）
   - かかったお金: 約$0.46（D-11）

6. **sonnet でもやろうとして、うまくいかなかった話**（体験談パート）
   - タスク一覧で haiku は Done、sonnet は Paused のまま（D-12）
   - 空応答・budget 関連の 400 エラー（D-13, D-14）と、試した設定変更（D-15）
   - 結論: thinking / budget の噛み合わせで今回は動かせず、比較は断念。原因の仮説と次に試すこと

7. **攻撃はログにどう見えたか**（記事の山場）
   - ALB風ログの読み方（E-1）
   - ステータス分布: 500/401/403/400 の多さが探索のサイン（E-2）
   - **SQLi の教科書的な痕跡**: `UNION SELECT NULL` で列数を探り → `Users` から資格情報 → `sqlite_master` でスキーマ列挙（E-3）
   - User-Agent とよく叩かれたパス（E-4）
   - アプリログ: `Solved` で攻撃の成立が見える（E-5）、**cheat 検知が「0分で攻略＝自動化」と判定**（E-6）、存在しない経路への探索（E-7）
   - 正解データとの突合: 116中18攻略、5★以上は0、XSS は0（E-8）
   - 3層の突合: 試したこと（アクセスログ）/ 成立したこと（アプリログ）/ 確定結果（Challenges）（E-9）

8. **実AWSとの違いと、CloudTrail に出ない理由**
   - CloudTrail は AWS API の操作記録（コントロールプレーン）なので、Webアプリへの攻撃（データプレーン）は本番でも出ない（E-11）
   - Flow Logs を見送ったことで見えなかったもの
   - どのログにも残らなかった行動 → 監視設計への示唆（E-12）

9. **まとめ**
   - 攻撃時の初動調査で見る順番: 時間窓を決める → 送信元・UAで串刺し → エラー率・件数の急増 → 何を狙ったか（ペイロード）→ 成否（アプリログ）
   - AIペンテスターの実力と限界: haiku でも4★まで自動で攻略、高難度・多段の攻撃は取り逃す
   - 次にやりたいこと: sonnet の再挑戦、nginx に WAF（ModSecurity）を入れて前後比較、Flow Logs 風ログの追加
