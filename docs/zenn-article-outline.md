## 方針

「構築に成功しました」という手順記事ではなく、**ツールの規約で途中で方針転換し、ローカルにAWS風のログ環境を作り直して、攻撃がログにどう見えるかを学んだ体験談** にする。
1本にまとめる想定。長くなりすぎたら、§6〜§7 を「ログ編」として2本目に分ける。

**仮タイトル案**
- 「AIペンテストツールARTEXをAWSで試すはずが、規約を読んでローカルに作り直した話」
- 「ARTEXの攻撃はログにどう見えるのか — ALB形式のログをローカルで再現して観察する」

**想定読者:** AWSは触ったことがあり、AIペンテスターの動きと、攻撃が防御側のログにどう出るかを知りたい人

## 構成

1. **はじめに**
   - 動機: 攻撃者視点（AIペンテスター）と防御側のログを両方見たい
   - 結論を先に: 「AWSではやらず、ローカルにAWS風ログ環境を作った。その理由と、見えたもの」

2. **最初の計画: AWSに検証環境を作る**（短く）
   - 当初の構成図（A-1）。Terraform で EC2 + Juice Shop + Flow Logs / CloudTrail / CloudWatch
   - admin を使わない IAM（A-2）、構築完了（A-3）
   - コラム: Fargate の vCPU 上限、PassRole 不足などのハマりどころ（A-4）

3. **規約の壁: 自分の環境でもネットワーク越しはダメだった**（記事の転換点）
   - ARTEX同梱の利用規約の該当箇所（B-1。引用は最小限＋出典）
   - 「自己所有だからOK」ではなく、ツール側の規約にも従う必要がある（B-2）
   - AWS環境は destroy（A-5）
   - 読者への注意: ペンテストツールを使う前に、対象の権限とツールの規約の両方を確認する

4. **ローカルに「AWS風ログ環境」を作り直す**
   - 構成図（C-1）と、AWSとの対応表（B-3）
     | AWS | ローカルでの代替 |
     |---|---|
     | ALB Access Logs | nginx（ALBと同じ29フィールド形式） |
     | CloudWatch Logs（アプリ） | Juice Shop の stdout |
     | VPC Flow Logs | 5タプル＋action 形式で模倣 `<<方式確定待ち>>` |
     | CloudTrail | 等価物なし（§7で説明） |
   - nginx の `log_format` で ALB 形式を再現する（C-2, C-3）
   - Flow Logs 風ログの出し方（C-4）
   - 平常時のログ（C-7）

5. **ARTEX を走らせる**
   - セットアップ: APIキーが必要（サブスクでは動かない）、既定モデルは高いので Haiku に変更（D-1, D-2）
   - 対象は `http://host.docker.internal:8080/`（D-3）
   - Planner の最初の計画、Worker の動き、API探索（D-5〜D-7）
   - Asset Graph / Exploration Graph の変化（D-8, D-9。GIF推奨）
   - 面白かった判断・失敗（D-10）、結果（D-11）
   - かかったお金（D-12）

6. **攻撃はログにどう見えたか**（記事の山場）
   - ALB風ログの読み方（E-1）
   - リクエスト数の急増、4xxの量産、パスの傾向、User-Agent（E-2〜E-4）
   - アプリログに残った攻撃ペイロード（E-5）と、通ってしまったリクエスト（E-6）
   - Flow Logs 風ログで見える／見えないもの（E-7）
   - **ARTEXの判断とログの時刻を並べる**（E-8）

7. **実AWSとの違いと、CloudTrail に出ない理由**
   - CloudTrail は AWS API の操作記録（コントロールプレーン）なので、Webアプリへの攻撃（データプレーン）は本番でも出ない（E-9）
   - ローカルで再現できなかったフィールドや挙動
   - どのログにも残らなかった行動 → 監視設計への示唆（E-10）

8. **まとめ**
   - 攻撃時の初動調査で見る順番: 時間窓を決める → 送信元で串刺し → 4xx率・件数の急増 → 何を狙ったか → 成否
   - 次にやりたいこと: nginx に WAF（ModSecurity 等）を入れて前後比較、ALB形式ログを Athena で読む
